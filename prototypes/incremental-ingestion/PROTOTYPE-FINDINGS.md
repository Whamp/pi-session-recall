# Incremental Recall Ingestion Prototype Findings

## Verdict

The approved architecture is viable with four constraints:

1. Keep projection payloads bounded and store source spans, not conversation text.
2. Let a write-capable worker recover zvec after a crash before read-only search resumes.
3. Commit evidence in short batches and close zvec between batches.
4. Build replacement generations beside the active generation; freeze incremental commits during rebuild, retain markers, then replay them after cutover.

The prototype supports moving to specification. It found no need for a daemon, per-entry projection documents, routine whole-session parsing, dual-generation writes, or search-worker IPC.

## Product recommendations

### Confirmed deletion should remove recall evidence

Recall promises source-backed evidence. Once the user intentionally deletes a session, keeping its recall documents would preserve content whose cited source no longer exists and would defeat the deletion.

Absence alone is not deletion. The worker should first set `source_missing`, confirm absence on a later metadata sweep, verify the session root itself is healthy, and refuse a suspicious mass deletion. Confirmation removes the physical projection, its logical projections, and every evidence occurrence from that source.

### Material backlog should be visible but never block search

Search should continue against the last durable generation. It should add one concise warning when eligible work has failed, a rebuild is serving an older generation, or the oldest eligible marker exceeds the service objective. Ordinary active-tail markers, expected quiescence waits, and brief write-window contention should remain silent.

The warning should contain scalar state only: pending eligible session count, oldest eligible age, and last failure category. It should contain no conversation text or source path.

## Measured evidence

The repeatable report is `prototype-results.json`, generated by:

```bash
npm run prototype:incremental-ingestion -- --report-only
```

All zvec writes used scratch collections under `.prototype-data/incremental-ingestion/`, which the harness removed after each run. The production recall collection was never opened.

### Scalar projection

| Active-tail JSON payload | Partial update p95 | Fetch p95 | Untouched fields preserved |
| -----------------------: | -----------------: | --------: | -------------------------- |
|                    1 KiB |           0.985 ms |  0.159 ms | Yes                        |
|                   64 KiB |           1.700 ms |  0.819 ms | Yes                        |
|                  256 KiB |           1.258 ms |  1.636 ms | Yes                        |
|                    1 MiB |           4.305 ms |  4.945 ms | Yes                        |
|                    4 MiB |          14.165 ms |  7.831 ms | Yes                        |
|                   16 MiB |         159.237 ms | 28.957 ms | Same-handle only           |

A 16 MiB payload updated five times failed read-only reopen in 10 of 10 isolated trials despite every zvec status reporting success. Fetch logged `doc_id ... segment not found`: the ID map knew the document, but `CollectionImpl::Fetch` could not find its segment. This is exact installed `@zvec/zvec@0.6.0` behavior, not a database-general assumption.

**Candidate bound:** cap each serialized logical active-tail projection at 1 MiB. Expected projections should be far smaller because they contain entry IDs, parent links, and source spans—not source text. Exceeding the cap sets `requires_reconciliation`; it must not silently truncate state.

Zvec document IDs also reject `:`. Stable projection IDs need a zvec-safe alphabet, such as an underscore prefix plus a hexadecimal digest.

### Crash recovery

After an intentional writer process exit:

- immediate read-only reopen did not expose the WAL-only document and logged a read-only recovery error;
- a read-write reopen recovered it;
- the following read-only reopen fetched it successfully.

The Node-pinned zvec core opens the writing segment with the collection’s `read_only` option and reconstructs in-memory writing components during recovery. The pinned crash tests reopen with write-capable options. Therefore a stale worker lock must keep search out until another write-capable worker has opened, replayed deterministic writes, committed projection state, and closed normally.

A normal writer close did preserve fresh scalar, dense, and FTS evidence. Fresh evidence remained fetchable and returned through both dense and lexical queries after read-only reopen even though vector `indexCompleteness` remained `0`. Incremental write windows do not need to optimize each batch; optimize remains explicit maintenance.

### Immediate bookkeeping

| Operation                                    |       p95 |
| -------------------------------------------- | --------: |
| Atomic marker write without fsync            |  0.202 ms |
| Marker file fsync + rename + directory fsync | 15.035 ms |
| Detached Node spawn call                     |  4.330 ms |
| Detached child exit                          | 21.561 ms |

**Candidate acceptance bound:** a Pi hook may durably publish a marker and ensure a detached worker in at most 25 ms p95 on this host. It must not await child exit or perform source parsing, tokenization, embedding, zvec access, or global-state parsing.

### Startup recovery

A metadata-only traversal of 3,512 session files totaling 2.384 GB took 72.261 ms p50 and 76.479 ms p95. Reading and parsing the existing 59.45 MB global `index-state.json` took 209.249 ms p95.

**Candidate policy:** the external worker may perform one coalesced metadata sweep after a new Pi runtime starts. Pi itself only publishes the arrival marker. Bound one sweep to 10,000 files or 500 ms; persist a continuation marker if either bound is reached. Never parse session bodies during discovery, and never parse the global state file in an interactive hook.

### Quiescence evidence

The prototype sampled 34 recently modified sessions totaling 100 MiB and observed 14,691 positive append gaps:

- p50: 1.492 seconds;
- p95: 56.501 seconds;
- p99: 1,413.084 seconds;
- 328 gaps (2.23%) reached 5 minutes;
- 135 gaps (0.92%) reached 30 minutes.

These gaps describe this bounded sample, not all future use. They support three scheduling candidates:

- compaction, branch-exit, or clean-departure transfer: wait for 60 seconds without growth;
- a transfer whose prepared work exceeds 32 documents: wait for 5 minutes without growth;
- crash-recovery eligibility based only on quiescence: require 30 minutes without growth.

The current prototype did not call the embedding server, so these remain initial host-specific values rather than universal defaults.

### Append-only worker preparation

The worker benchmark copied recent sessions in three size bands, loaded the pinned Octen tokenizer from copied cache assets, and measured LF-boundary verification plus parse/tokenize work for the last 10, 50, and 200 complete records.

- Tokenizer cold load: 227.171 ms and about 33.6 MB additional RSS.
- Boundary verification: at most 4.198 ms p95 across the measured deltas.
- A 23.6 MB session required 1,396.361 ms for full preparation, but only 5.035 ms p50 for its final 200 records: a 277× reduction.
- A 4.8 MB session required 167.431 ms in full, versus 51.131 ms p50 for its final 200 records and 0.405 ms for its final 10.
- The small 123 KB sample contained only five very large records. Its delta therefore covered the whole file and still cost about 30 ms. Append cursors cannot avoid processing one genuinely new huge record; they avoid reprocessing earlier records.
- A scratch content-addressed cache resolved 75 warm vector files in 3.481 ms. Creating 75 placeholder misses took 5.482 ms before any model request. Real cache misses still pay embedding-server cost and were deliberately not invoked.

The worker should inspect marker eligibility and file metadata before loading the tokenizer. Activity markers that have not reached an eligibility boundary should therefore exit without paying the 227 ms tokenizer startup cost.

### Zvec write windows

Scratch evidence used 2,560-dimensional vectors plus FTS and HNSW fields.

| Documents | Full open/write/close p50 |        p95 |
| --------: | ------------------------: | ---------: |
|         1 |                190.299 ms | 255.655 ms |
|         8 |                196.116 ms | 232.868 ms |
|        32 |                218.344 ms | 265.993 ms |
|       128 |                259.324 ms | 298.191 ms |

Open and close dominate small batches. Batching 32 documents amortizes that cost while keeping the measured exclusive window below 300 ms p95.

**Candidate policy:** use batches of at most 32 evidence documents and target a 300 ms p95 write window. A search may wait up to 500 ms for the current window, then returns a specific busy error. These are initial host-specific bounds, not universal zvec guarantees.

## Transition model

`TRANSITIONS.md` covers initial batched persistence, normal appends, repeated and split-turn compaction, branch navigation with and without summaries, clean switches, reload, quit, force exit, fork, clone, import, deletion, rewrite detection, and historical formats.

All scripted reducer checks passed for:

- monotonic repeated compaction;
- abandoned branch eligibility without indexing the new active tail;
- idempotent replay after evidence upsert and worker crash;
- frozen incremental commits plus marker replay into a replacement generation;
- evidence removal after confirmed source deletion.

The reducer is intentionally smaller than Pi’s parser. The specification must preserve the strict graph parser as the explicit reconciliation oracle rather than making the append parser support historical formats or arbitrary rewrites.

## Generation cutover

`GENERATION-CUTOVER.md` rejects dual-generation incremental writes. During an explicit rebuild:

- searches keep using the old active generation;
- incremental commits freeze while markers accumulate outside zvec;
- the rebuild creates and optimizes a new generation beside the active one;
- a short lock atomically swaps a checksummed active-generation pointer;
- the ordinary worker replays retained markers into the new projection;
- the old generation remains rollback material.

This changes `--rebuild` from destructive replacement to side-by-side construction. It avoids a multi-hour search outage and keeps one incremental write target.

## Diagnostic and acceptance candidates

Record scalar-only worker diagnostics for marker age, metadata sweep, bytes appended, entries parsed, eligible documents prepared, tokenizer time, embedding-cache hits and misses, embedding requests, zvec lock wait, open/write/close, projection commit, marker acknowledgement, and generation ID.

The later implementation should prove:

- Pi hook p95 ≤ 25 ms;
- zero session parsing, tokenization, embedding, zvec access, or global-state parsing in Pi hooks;
- append processing reads only the boundary verification window and bytes after the durable cursor;
- projection payload ≤ 1 MiB;
- metadata sweep p95 ≤ 500 ms within the 10,000-file bound;
- evidence batches ≤ 32 and zvec write-window p95 ≤ 300 ms on the target host;
- search waits ≤ 500 ms for one write window and never waits for ingestion completion;
- marker deletion occurs only after the target generation’s projection checkpoint is durable;
- writer crash recovery precedes read-only reopen;
- rebuild leaves active search available and marker replay idempotent;
- failed or materially stale eligible work appears as a scalar backlog warning;
- no source session, production zvec generation, embedding cache, or user configuration is mutated by evaluation.

## Ready for specification

The five engineering investigations are complete at prototype depth:

1. scalar projection and zvec recovery behavior;
2. quiescence, append preparation, cache resolution, and write-window bounds;
3. startup metadata sweep cost and bounds;
4. Pi session transition table;
5. side-by-side rebuild cutover, marker replay, diagnostics, and acceptance candidates.

The remaining choices are the two product policies above: confirmed deletion and materially stale backlog warnings. If accepted, the next step is a handoff of these findings, followed by the implementation specification and tickets. Production implementation must re-establish the thresholds with integration diagnostics; the throwaway prototype is evidence for the design, not production code.
